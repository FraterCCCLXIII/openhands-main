<p>Most developers using AI are using it to accelerate the <em>inner loop</em> of development. They&#x27;re using an AI-powered IDE or a CLI agent, running locally on their laptop. As they make progress, tweaking the code and checking the results, the AI helps them go a bit faster.</p><p>On the other hand, there&#x27;s an emerging paradigm of cloud-based agents that shine in the <em>outer loop</em>. Devs invoke agents from Slack, Jira, and GitHub to take on entire tasks, without ever having to open their IDE.</p><p>In this blog I&#x27;ll describe a bit about this emerging paradigm, and argue that the most effective developers and development teams will be using both.</p><h1>Inner and Outer Loops</h1><p>The terms for inner and outer loops of development <a href="https://web.archive.org/web/20180107111725/https://mitchdenny.com/the-inner-loop/">emerged in the late 2010s</a>, as developers reoriented around containers and cloud native applications.</p><p>The inner loop is what you probably think of when you think about coding. Make a small change to the code, then see if it works by loading the app or running the tests; rinse and repeat until you&#x27;re happy with your changes. The inner loop takes place entirely on your laptop, usually without anyone else involved.</p><p>The outer loop kicks in after you <code>git push</code>. This is where your team&#x27;s tooling kicks into gear: CI/CD pipelines, code review, issue tracking, etc. The outer loop happens in the cloud, and is also where your teammates start to get involved.</p><p>Typically in the inner loop, you get to bring your own tooling: you can use whatever IDEs, CLIs, etc you want. I&#x27;m a neovim user, but my teammates have their own preferences like VS Code, Zed, or Cursor—fortunately in the inner loop it doesn&#x27;t matter if we&#x27;re using different tools.</p><p>In the outer loop, the team needs to settle on tooling together. It wouldn&#x27;t make any sense for me to use Jira while you use Linear! Or for me to use GitHub while you use GitLab. The outer loop is where we collaborate.</p><h1>Inner Loop Agents</h1><p>So far, AI has mostly entered the inner loop of development. Developers are running agents inside <a href="https://docs.openhands.dev/openhands/usage/run-openhands/acp#acp-integration">their IDE</a> or <a href="https://docs.openhands.dev/openhands/usage/run-openhands/cli-mode">as a CLI</a>.</p><p>The agent can take over most of the rote work of actually writing lines of code, while the developer thinks more deeply about the particular problem they&#x27;re working on. The agent serves as an assistant, a pair programmer helping the developer move faster through the inner loop.</p><p>This does seem to lift productivity a bit. According to research studies developers can see something like a 40-50% productivity gain in implementation (sources: <a href="https://arxiv.org/abs/2507.08149">1</a>, <a href="https://papers.ssrn.com/sol3/papers.cfm?abstract_id=5713646">2</a>), although often at the cost of increased debugging time (<a href="https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/">source</a>). But using agents is also a practicable skill! Agents are tricky, but once you get a feel for where they work well and where they fall down, having an agent coding with you feels like wearing a jetpack.</p><p>The gains here are incremental though. The developer is still actively focused on the task at hand; the AI is just helping them go a bit faster. It&#x27;s a far cry from the &quot;fully autonomous AI developer&quot; we were promised!</p><h1>Outer Loop Agents</h1><p>Increasingly, devs are starting to figure out how to run agents in the outer loop.</p><p>In the outer loop, agents run on <em>their own</em> infrastructure, instead of on your laptop. They might run inside of a GitHub Action, a Kubernetes pod, or on a service like <a href="https://app.all-hands.dev/">OpenHands Cloud</a>. They get their own filesystem, their own terminal, their own web browser, and their own copy of your codebase.</p><p>There are two major implications here: <em>safety</em> and <em>scalability.</em></p><h2>Safety</h2><p>When you run a local agent, there&#x27;s nothing stopping it from running <code>rm -rf /</code> or exfiltrating your AWS credentials. That&#x27;s why local agents have an option to repeatedly ask you to hit the <code>y</code> key to confirm their next action—you need to babysit them to be sure they don&#x27;t do anything harmful.</p><p>When the agent runs in its own infrastructure, the blast radius is much smaller. The agent only has access to the tools and credentials you explicitly connect. You can let it run unsupervised with greater confidence (so long as you&#x27;re not adding things like AWS keys of your root account into the environment!)</p><p>When agents run in the outer loop, developers typically let them run completely autonomously, without babysitting and approving every individual action.</p><h2>Scalability</h2><p>Running in the cloud also offers far more scalability than running local agents.</p><p>Sure, you can run a few different agents at the same time locally. But with each agent, you increase the chances that they&#x27;ll try to edit the same file, or run commands that compete for resources. And of course, you&#x27;ll also need to watch them and approve their actions. Most developers hit a limit at around 2-3 local agents.</p><p>In the cloud, we can scale to dozens—even thousands!—of agents without breaking a sweat. Each one gets its own workstation, its own memory and CPU. Things might get <em>expensive</em>, but in the cloud there&#x27;s nothing stopping us from spinning up another VM or container for our agent to work in.</p><p>The big question is: <em>what can we do with 1000s of agents?</em></p><h1>Tech Debt and Toil</h1><p>Most developers want to spend their time <em>shipping features</em>. Sure, some of us really love a good refactor, or tuning the logs, or updating old dependencies. But what gets us excited (and promoted) is shipping new value to end users.</p><p>But every large codebase sits on a mountain of tech debt. Dependencies rot and go out of support. Decisions made last year no longer make sense. New open source vulnerabilities get announced, leaving you exposed to attack. Some teams spend a majority of their time just keeping the lights on.</p><p>Fortunately this work is often easy to automate! Even before LLMs, we got used to services like Dependabot upgrading dependencies for us, automatically putting up PRs for review. And with LLMs, the scope of work we can address with automation increases by an order of magnitude.</p><h2>Example: CVE Remediation</h2><p>A great example here is CVE (Common Vulnerability/Exposure) remediation. Every day, new open source vulnerabilities are announced. Every team has a backlog of tens to thousands of known vulnerabilities in their codebase, which often languishes until someone from the security team complains.</p><p>The process of remediating CVEs is a pain. You need to figure out where the vuln is coming from, and what exactly needs to be updated (package.json? A Dockerfile? something else?). Worse, the update might include breaking changes, forcing you to modify your codebase as well. Finally, you need to ensure everything works and that the CVE has indeed been resolved.</p><p>But it&#x27;s a very rote process, so agents are a great fit for CVE resolution!</p><p>Now, you <em>could</em> do this with inner loop agents. You could assign each CVE to a developer, and have that developer work with an agent locally to fix the CVE. That&#x27;d be closest to how we&#x27;re used to working.</p><p>But what if you kicked off an outer loop agent <em>immediately</em> after the CVE was announced? The agent can run completely on its own, researching, resolving, and verifying a fix. And it can automatically open up a pull request for the team to review, without needing a human supervisor.</p><p>This is much closer to how pre-AI automation like Dependabot work. PRs magically appear, and the devs just have to spot-check and merge it.</p><p>And yes—for the largest companies working with OpenHands, this often does imply running 100s or 1000s of concurrent agents when a new CVE is announced—you need one for each affected repo!</p><p>See more details in <a href="https://openhands.dev/blog/remediating-cves-at-scale-with-agents">our blog</a> on the topic.</p><h2>Example: Error Log Resolution</h2><p>A great target for any team is to get to zero error logs in production. Info and warning logs are helpful; error logs are a sign something is going wrong.</p><p>We&#x27;ve helped some teams enact this by setting up OpenHands to scan their Datadog logs for new error patterns. The agent then follows a workflow to figure out which repository is triggering the error, and finds the right part of the codebase. It can then fix the problem, add better error handling, or downgrade the log to a warning.</p><p>So even if the error occurs at 3am, the team wakes up to a proposed fix the next morning!</p><p>This is a great example of the sort of toil that slowly builds, with no clear owner. But thoughtful use of agents can help developers keep their production deployments clean and healthy without taking energy from the team.</p><p>We have more details on this one in <a href="https://openhands.dev/blog/debugging-production-issues-with-ai-agents-automating-datadog-error-analysis">a blog</a> as well.</p><h1>You Can Have Both</h1><p>We&#x27;re finding that there&#x27;s a place for agents in both the inner loop and the outer loop.</p><p>Inner loop agents are great for <em>ad hoc</em> work: if you&#x27;ve got a new feature to implement, or a tricky bug you&#x27;re trying to uncover, you&#x27;ll probably work best inside an IDE—but having an agent there with you to take on smaller bits of the task can be a great lift.</p><p>Outer loop agents are great for <em>repeatable</em> work: if you&#x27;re toiling away at the same annoying chores, you can probably craft a prompt that will drive an agent through the same process. This is a great way to keep your maintenance backlog at bay.</p><p>You might want to use the same solution for both (OpenHands provides both <a href="https://docs.openhands.dev/openhands/usage/run-openhands/cli-mode">a CLI for the inner loop</a>, and <a href="https://github.com/OpenHands/software-agent-sdk">an SDK for the outer loop</a>). But more likely, you&#x27;ll want to let each dev on your team choose their own inner loop tooling, and standardize on a single solution for the outer loop.</p><p>Just make sure you&#x27;re not sleeping on the outer loop!</p>
