<p><em>This is a guest blog by </em><a href="https://hydrapse.github.io/"><em>Gangda Deng</em></a><em> and </em><a href="https://czlll.github.io/"><em>Zhaoling Chen</em></a><em>, introducing EvoClaw—a benchmark built with OpenHands to move beyond isolated coding tasks and toward continuous software evolution.</em></p><p>AI coding has entered a new phase. In early 2026, stronger LLMs and projects like <a href="https://github.com/openclaw/openclaw">OpenClaw</a> started pushing agents toward long-running, iterative workflows instead of one-off conversational task solving.</p><p>Most benchmarks still evaluate isolated tasks. Agents are getting good at those. But real engineering work is not one isolated task. Teams continuously extend an existing codebase while preserving behavior, managing dependencies, and paying down technical debt.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fb784a2fdfe16cbf27dc_cover.webp" loading="lazy" alt=""/></div></figure><p>Continuous development is where software engineering really begins. Early implementation choices constrain later work, regressions accumulate, and the real question becomes: can an agent keep solving the next task without degrading the system in the process?</p><p>That is what <a href="https://evo-claw.com/">EvoClaw</a> is designed to measure. It evaluates agents on <strong>continuous software evolution</strong> by asking them to complete a sequence of dependent milestone tasks extracted from real repository history.</p><h2>From isolated tasks to continuous evolution</h2><p>EvoClaw is built around a simple observation: one-shot code generation is not how most software is developed. Requirements arrive over time, each change depends on earlier decisions, and the system has to stay healthy while it evolves.</p><p>The benchmark captures that setting by reconstructing milestone trajectories from real repositories and evaluating agents across those trajectories instead of on isolated bug-fix prompts.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fba38e8ed0edb46cd1bf_benchmark-overview.webp" loading="lazy" alt=""/></div></figure><h2>Why milestones matter</h2><p>Milestone-level task granularity is the key design choice in EvoClaw.</p><p>‍</p><p>A single commit is often too small and too noisy to serve as a meaningful development objective. At the other extreme, release-level changes are too coarse and hide the dependency structure that makes long-horizon maintenance difficult. EvoClaw works at the milestone level: semantically and functionally coherent units that are still executable and testable.</p><p>To build those trajectories at scale, the authors introduce <strong>DeepCommit</strong>. Starting from real open-source history, DeepCommit aggregates related commits into milestones, infers temporal dependencies, and validates the resulting task graph at runtime.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fbf4a1d939053d85d6d7_milestone-dag.webp" loading="lazy" alt=""/></div></figure><h2>What EvoClaw measures</h2><p>EvoClaw covers repositories across <strong>five programming languages</strong>. For each repository, it selects a real development window spanning multiple releases, sometimes across as much as 750 days of history.</p><p>The benchmark focuses on two complementary dimensions:</p><ul role="list"><li><strong>Recall</strong>: how much of the newly required functionality the agent implements</li><li><strong>Precision</strong>: how much existing functionality the agent preserves without introducing regressions</li></ul><p>Those two signals are then combined into a milestone-level score using an F1-style aggregation.</p><p>This framing matters because the hard part of real software evolution is often not adding new code. It is keeping the existing system from breaking while the codebase gets more complicated.</p><h2>The headline result</h2><p>The results drop sharply once evaluation moves from isolated tasks to continuous evolution.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2a00864acdcfca728ebfc_202603-evoblog-1.webp" loading="lazy" alt=""/></div></figure><p>On isolated-task settings, frontier agents can often score above 80%. But under EvoClaw&#x27;s continuous setting, the best system in the initial release reaches only <strong>38.03% overall score</strong>: <strong>Claude Opus 4.6 + OpenHands</strong>. The highest resolve rate is <strong>13.37%</strong>, achieved by <strong>Gemini 3 Pro + Gemini CLI</strong>.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fc123cf57e1ba7e0d231_main-results.webp" loading="lazy" alt=""/></div></figure><p>That gap is the central point of the benchmark: isolated-task performance still overestimates how well an agent will behave once earlier choices, regressions, and dependency chains start to matter.</p><h2>Evolution eventually stalls</h2><p>A natural question is whether a strong coding agent could eventually finish the whole project if you simply gave it enough iterations.</p><p>EvoClaw suggests the answer is no.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fc24a7ef93eb9c29aeaf_evolution-plateau.webp" loading="lazy" alt=""/></div></figure><p>Even the strongest system, Opus 4.6, plateaus at roughly <strong>45% overall score</strong> under saturation-based extrapolation. The differences across model families are also revealing: GPT and Claude improve steadily across versions, while Gemini variants often start faster in the early milestones but show much less long-horizon improvement.</p><p>A more interesting pattern appears when the overall score is decomposed into recall and precision.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fc314362153174bb12fd_recall-vs-percision.webp" loading="lazy" alt=""/></div></figure><p>Recall keeps rising almost linearly. Even as the codebase becomes messier and more fragile, agents remain fairly good at implementing new requested functionality. The bottleneck is precision: models struggle to preserve existing behavior, and regressions accumulate faster than they can be repaired.</p><p>That is what ultimately causes long-horizon development to stall.</p><h2>Technical debt compounds faster than agents can repair it</h2><p>To understand how failures compound over time, the benchmark introduces an <strong>error chain</strong> analysis that tracks how problems propagate across milestones.</p><figure class="w-richtext-align-center w-richtext-figure-type-image"><div><img src="https://cdn.prod.website-files.com/68ff4058b35616cdd47d5b59/69c2fc3e0d72c4c863e43bd8_error-chain-analysis.webp" loading="lazy" alt=""/></div></figure><p>The pattern is clear. Agents do sometimes repair earlier mistakes, but unresolved regressions accumulate faster than they can be fixed. Those failures then propagate downstream through dependency chains, creating a snowball effect that eventually stalls further progress.</p><h2>From code generation to system governance</h2><p>If EvoClaw makes one thing clear, it is that code generation alone is not enough. The real entry point for AI systems into software engineering is whether they can follow evolving requirements while also keeping the larger system stable.</p><p>Today&#x27;s frontier models still behave more like on-demand code generators than like senior engineers maintaining a living codebase. They are much better at local implementation than at system-level judgment.</p><p>That points to where the next breakthroughs need to happen: proactive refactoring, long-term memory, better planning, and much stronger awareness of architectural state. It is the same shift described in <a href="https://ysymyth.github.io/The-Second-Half/">The Second Half</a>: moving from passive code generation toward active system governance.</p><p>If you want to dig deeper, the full project is available here:</p><ul role="list"><li><a href="https://evo-claw.com/">Leaderboard</a></li><li><a href="https://arxiv.org/abs/2603.13428">Paper (arXiv)</a></li><li><a href="https://huggingface.co/datasets/hyd2apse/EvoClaw-data">Dataset</a></li><li><a href="https://github.com/Hydrapse/EvoClaw">Code</a></li></ul>
